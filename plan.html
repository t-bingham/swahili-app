Guiding Principle

Build capability-by-capability, not language-by-language. Swahili should become the first language adapter, not the hidden default. Korean and MÄori should prove that the same app can provide language-specific support through pluggable modules.

Why This Matters

The current app began as Swahili, so Swahili-specific assumptions live in names, labels, grammar hints, error classification, and exercises. Adding Korean/MÄori by copying those patterns would work briefly, then become expensive.

The target is a small multilingual engine where each language provides what it needs: grammar hints, error classifiers, exercise types, TTS preferences, generated practice metadata, and cultural support.

Target Architecture

Language Adapter Registry

Add a behavior layer alongside the existing language metadata registry.

interface LanguageAdapter {
  id: string;
  targetLabel: string;
  englishLabel: string;
  ttsLangs: string[];

  grammarHint(card): string | null;
  scaffoldHint(card): string | undefined;
  classifyError(args): ErrorType;
  acceptsAnswer(args): boolean;
  specialExercises(card): ExerciseCandidate[];
}
  • Metadata stays in src/data/languages.ts: name, flag, script, template DB, broad features.
  • Behavior moves to src/languages/sw.ts, src/languages/ko.ts, src/languages/mi.ts.
  • Fallback adapter provides generic flashcard/multiple-choice/type-answer behavior for future languages.

Future Languages

New Language Checklist

  • Add language metadata: id, names, flag, script, seed DB path, broad features.
  • Add a minimal adapter using generic fallback behavior.
  • Define its grammar capabilities before writing special exercises.
  • Create a seed builder and content-review export path.
  • Launch first with generic flashcard/MC/type-answer if needed.
  • Add special exercises only where they naturally match the language.
  • Add adapter tests for grammar hints, answer acceptance, and structural error classification.
Rule of thumb: language-specific content belongs in data/builders/adapters. Shared screens should ask the adapter what to do instead of checking language IDs directly.

Implementation Order

Suggested Sequence

  1. Adapter boundary: create the registry and move Swahili grammar hints into it.
  2. UI labels/audio: remove the most visible Swahili-only strings and TTS assumption.
  3. Korean/MÄori grammar hints: use existing generated metadata to provide useful wrong-answer feedback.
  4. Error classifiers: add Korean and MÄori structural classifiers.
  5. Special exercise registry: refactor Swahili special exercises behind the adapter, then add Korean particle and MÄori tense drills.
  6. Metadata cleanup: complete - generated tags and keys are standardized in the Korean/Maori builders.
  7. Review loop: complete - Sheets export remains available and the in-app review queue is language-aware.
This plan intentionally preserves the current local-first architecture. It improves learning intelligence inside the existing app before any Convex/native/offline-pack migration work.
