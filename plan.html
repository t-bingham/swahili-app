Architecture Hardening Plan

A practical roadmap for turning the multilingual learning app into a more reliable, language-neutral, offline-first product without forcing a premature backend or native rewrite.

Source: code review findings, current app architecture, and the decision to keep validating the learning experience before a full Convex or native migration.
Decision Architecture Principles Implementation Phases Tracked Findings Future Stack Readiness Acceptance Checks Working Notes

Decision

Recommendation: keep the current static, offline-capable React + SQLite architecture for now, but refactor it toward clear boundaries that match the eventual app architecture. This avoids a big rewrite while making a future Convex, Capacitor, or native move much easier.
Do Now Stabilize tests, language adapters, curriculum review, and offline data boundaries.
Do Next Make sync and content import/export explicit so the app can grow beyond Google Drive.
Do Later Move to Convex when shared accounts, publishing, moderation, and analytics justify it.
Keep The current low-cost, offline-first prototype loop while friends are testing.

Architecture Principles

Build Boundaries Before Rebuilding

Separate curriculum data, learner progress, language-specific intelligence, and sync behavior inside the current app first. These boundaries are the real migration work.

Language-Neutral Core

The learning session, spaced repetition, review logs, and offline storage should not know whether the user is learning Swahili, Korean, or Maori.

Language Adapters Own Specifics

Grammar prompts, special exercises, pronunciation rules, cultural notes, answer aliases, and feedback should live behind a consistent adapter interface.

Offline First, Sync Second

Downloaded curriculum and local progress remain the source of the user experience. Sync should reconcile compact changes rather than replace the local app.

Implementation Phases

1
CompletedReliability

Reliability and Test Baseline

Make the app safer to change before larger refactors. The stale database regression tests now match the migrated database layer, and the full verification loop is green.

  • Fix stale or failing test expectations documented in review.html.
  • Add focused regression coverage around the migration structure and language-scoped migration boundary.
  • Keep npm run build passing as the primary gate.
  • Document remaining known warnings as follow-up work instead of blocking Phase 1.
2
CompletedLanguage Parity

Language Adapter Cleanup

Swahili concord parsing now has one language-layer source of truth, and adapter parity tests cover Swahili, Korean, and Maori special-exercise selection.

  • Define a single adapter contract for special exercises, answer checking, pronunciation, hints, examples, and review labels.
  • Make Swahili, Korean, and Maori adapters implement the same surface area.
  • Remove duplicated Swahili concord parsing from the adapter/component split.
  • Add adapter capability tests for all supported languages.
3
CompletedHuman Review

Curriculum Review Workflow

The review screen now supports local curriculum audit notes, selected-card review, note export, and accepted correction patches that can feed the seed database update process.

  • Expose a clear review entry point from visible cards and curriculum views.
  • Store review notes with card id, language, issue type, suggested correction, reviewer, and timestamp.
  • Add export tools for review notes so manual review can happen outside the app if needed.
  • Keep correction patches available for accepted fixes to update public/swahili_default.db and future migrations.
4
CompletedPortability

Offline Package and Data Boundary

The app now records installed curriculum package metadata, installed unit versions, and has an export boundary for local progress changes that future sync/download work can use.

  • Identify which tables are curriculum truth and which are user-owned progress.
  • Add metadata for language pack version, unit version, and installed curriculum scope.
  • Add a compact local progress-change export boundary for future sync payloads.
  • Keep current SQLite local storage, but make the schema ready for unit-by-unit downloads.
5
CompletedConvex Ready

Sync Boundary for Future Backend

Google Drive now sits behind an app-level sync provider interface, and app screens call the provider-neutral sync service instead of importing Drive directly.

  • Create explicit sync operations for sync, provider support, last-sync state, and local state clearing.
  • Keep Google Drive as one implementation, not the app's sync model.
  • Define future Convex collections for users, curriculum versions, review notes, progress deltas, and sync cursors.
  • Do not require a backend for normal local practice sessions.
6
CompletedCapacitor

Capacitor Readiness

Browser-specific file export and speech APIs now sit behind platform wrappers, and the project has a Capacitor readiness map for native storage, auth, audio, exports, cache, and notifications.

  • Audit IndexedDB, WASM, PWA service worker, and Google auth behavior under Capacitor constraints.
  • Isolate platform services for file export and audio, with remaining native services tracked explicitly.
  • Confirm the app still builds as the current web/PWA target before adding native packaging.
  • Document likely native plugin needs before starting app store work.

Future Stack Readiness

Convex Later

Convex should become attractive when the app needs shared reviewer roles, multi-device accounts, curriculum publishing, analytics, moderation, and server-side sync. Until then, keep it as a planned destination rather than a dependency.

Prepare now by defining:

  • Stable ids for cards, units, languages, users, review notes, and progress events.
  • Versioned curriculum packages and migrations.
  • A small sync contract that can map to Drive today and Convex later.

Capacitor Later

Capacitor should be a packaging step after the web app is stable. The current React app is a reasonable base, but platform services need to be isolated so iOS and Android do not inherit browser-specific assumptions.

Prepare now by isolating:

  • Storage and database loading.
  • Google auth and account switching.
  • Audio, notifications, file export, and offline package downloads.

Acceptance Checks

  • The app still runs as a static Vercel-deployable site.
  • npm run build passes after each phase.
  • Tests cover the refactored adapter and review boundaries.
  • Swahili, Korean, and Maori remain usable after each phase.
  • Friends can review curriculum without editing raw SQLite manually.
  • The path to Convex and Capacitor is clearer, but neither is required for the prototype to keep working.

Working Notes

This plan intentionally favors architecture hardening over a rewrite. The purpose is to make each improvement useful immediately while reducing the cost of a future backend or native app.

Implementation Rule

Each phase should leave the app in a shippable state. If a refactor cannot be completed safely in one pass, add the boundary first, keep the old implementation behind it, then migrate call sites incrementally.
